# server/ — операции по хостам

Ansible-набор для регулярных операций по домашним хостам: аудит состояния,
off-site бэкапы, ротация ключей, правила firewall для docker-публикаций, уборка легаси.

Появился как результат инвентаризации 2026-09-18: всё, что там нашлось важного,
здесь либо автоматизировано, либо проверяется.

## Хосты

| Хост | Адрес | Роль | sudo |
|---|---|---|---|
| `omamac` | локально (control node) | рабочая станция, Arch Linux ARM | требует пароль |
| `cloudcode` | 100.73.91.4 | VPS сервисов (Ubuntu 24.04) | **нет** |
| `proxy` | 100.121.120.33 | VPS VPN/proxy-шлюз (Ubuntu 24.04) | passwordless |

## Требования

- SSH-доступ к хостам (ключи), `omamac` — локальный control node.
- Ansible: `bin/ops` сам поставит `ansible-core` через `uv`, если его нет.

```bash
cd server
./bin/ops help
```

## Команды

| Команда | Что делает | Риск |
|---|---|---|
| `./bin/ops audit` | read-only: публичные порты, состояние контейнеров, свежесть бэкапа, права на файлы с секретами, аккаунты-наследники, правила DOCKER-USER | нет |
| `./bin/ops backups` | ставит restic, рендерит `backup.sh`/`verify-restore.sh`, env с ключами, cron; инициализирует репозиторий | низкий |
| `./bin/ops verify` | `restic check` + реальное восстановление + `PRAGMA integrity_check` + сверка содержимого | нет |
| `./bin/ops rotate-s3` | обновляет S3-ключи на хостах, проверяет их работоспособность, при неудаче откатывает файл | средний |
| `./bin/ops docker-firewall` | правила `DOCKER-USER`: whitelist портов, остальное с аплинка — DROP. **Применение выключено по умолчанию** | высокий |
| `./bin/ops cleanup` | удаление легаси-каталогов/контейнеров/юнитов/аккаунтов. **Применение выключено по умолчанию** | высокий |
| `./bin/collect-secrets` | сборка всех ключей/кред трёх хостов в один зашифрованный архив (не Ansible, отдельный скрипт) | нет (только чтение) |

Любой прогон `ops` ограничивается хостом: `./bin/ops audit --limit proxy`.

## Сборка секретов: `bin/collect-secrets`

Ansible-ролями секреты не соберёшь, поэтому есть отдельный скрипт: он обходит
три хоста и складывает всё, без чего не восстановить ни хосты, ни restic-репозитории.

```bash
./bin/collect-secrets                        # спросит парольную фразу
OUT_DIR=/mnt/usb ./bin/collect-secrets       # куда положить
BUNDLE_PASSPHRASE=... ./bin/collect-secrets  # неинтерактивно (cron)
```

- Результат — `secrets-bundle-<YYYYmmdd-HHMMSS>.tar.gz.gpg` (0600), симметричное
  шифрование gpg AES256; парольная фраза нигде не сохраняется, её место — Bitwarden
  (туда же вложением сам архив). Архивы копятся по одному на прогон: распаковывать
  нужно по имени файла, маска `secrets-bundle-*.gpg` при двух файлах ломает `gpg -d`
  (`usage: gpg [options] --decrypt [filename]`).
- Внутри: `README.md` (что где лежит и как восстанавливать), каталог на хост,
  `MANIFEST.tsv` (что собрано), `GAPS.txt` (что не собрано и почему),
  `CRON-<host>.txt`, `RESTIC-REPOS.txt` (несекретные адреса репозиториев).
- Источники: `omamac` локально, `cloudcode` по ssh, `proxy` по ssh + `sudo -n`.
  Открытый текст живёт только в `mktemp`-каталоге 0700 и удаляется при выходе.
- Ключи Amnezia лежат **внутри контейнеров** (`/opt/amnezia` на хосте — только
  Dockerfile'ы), поэтому скрипт дополнительно выгружает `/opt/amnezia`,
  `/etc/ipsec*`, `/etc/wireguard`, `/etc/3proxy` из работающих amnezia-контейнеров.
- В конце идёт самопроверка: архив расшифровывается той же фразой, а список файлов
  внутри сверяется с собранным деревом; при расхождении скрипт падает.
- Чего не будет: приватных SSH-ключей из Bitwarden-агента (они не на диске).
  Root-only файлы `cloudcode` (`/opt/dockhand`, `/etc/rclone`, том dockhand)
  собираются через `~/root-dump`: `mfesenko` в группе `docker`, поэтому достаточно
  `docker run -u 0` с bind-mount этих путей (однострочник — в README внутри архива).
  Пока каталога нет, в `GAPS.txt` висит одна строка `НЕТ: /home/mfesenko/root-dump`.

## Секреты

Репозиторий публичный, поэтому секретов в нём нет вообще. Варианты передачи:

```bash
# 1) ansible-vault (рекомендуется)
cp group_vars/vault.yml.example group_vars/vault.yml
$EDITOR group_vars/vault.yml
ansible-vault encrypt group_vars/vault.yml
./bin/ops backups --ask-vault-pass

# 2) разово через extra-vars
./bin/ops rotate-s3 \
  -e s3_access_key_id='<tenant_id>:<key_id>' \
  -e s3_secret_access_key='<secret>' \
  -e restic_password='<пароль-репозитория>'
```

`group_vars/vault.yml` в `.gitignore`. Ключи Cloud.ru имеют вид `<tenant_id>:<key_id>` —
двоеточие обязательно, это не опечатка.

## Ротация ключей: как это выглядит

1. В консоли Cloud.ru создаёшь **новый** ключ доступа.
2. `./bin/ops rotate-s3 -e s3_access_key_id='...' -e s3_secret_access_key='...'`
   — роль обновляет env-файл на cloudcode и proxy, затем проверяет ключ реальным
   запросом к репозиторию restic.
3. Если ключ не работает — файл автоматически возвращается к предыдущему
   (бэкап рядом: `<env>.bak-<timestamp>`), плейбук падает с внятной ошибкой.
4. Убедившись, что всё зелёное, отзываешь старый ключ в консоли Cloud.ru.
   Старый ключ нельзя отозвать раньше: пока он жив, бэкапы продолжают работать.

## Что закрыто из инвентаризации

| Находка инвентаризации | Где закрыто |
|---|---|
| бэкапов нет нигде | роль `restic_backup` (cloudcode → SFTP + S3; proxy → S3) |
| проверка восстановления «на словах» | `verify.yml` + `verify_templates/verify-restore.sh.j2` |
| S3-ключи в чате/на хостах вручную | роль `s3_keys` с проверкой и откатом |
| публикация docker-портов в обход input-цепочки | роль `docker_firewall` |
| контейнеры без healthcheck, paused с открытым портом | проверка в `audit` |
| файлы с секретами не 0600 (`snx-rs.conf` и пр.) | проверка в `audit` |
| аккаунты-наследники (`alarm`, `hiddify-*`) | проверка в `audit`, удаление в `cleanup` |
| мусор (старые бэкапы Hiddify, мёртвые контейнеры) | `cleanup` |
| ключи Amnezia лежат внутри контейнеров, а restic бэкапит `/opt/amnezia` с одними Dockerfile'ами | `bin/collect-secrets` выгружает конфиги из контейнеров |

## Безопасность изменений

- `audit` и `verify` — только чтение, можно запускать в любой момент.
- `backups` идемпотентен: повторный прогон не меняет ничего, если всё уже на месте.
- `docker-firewall` и `cleanup` по умолчанию **ничего не применяют**; сначала
  `--check`, затем осознанное `-e docker_firewall_apply=true` / `-e cleanup_apply=true`.
- Откат `docker-firewall` — одной командой на хосте: `sudo iptables -F DOCKER-USER`
  (цепочка наполняется только этой ролью, поэтому чистка возвращает прежнее состояние).
- Правила firewall привязаны к входному интерфейсу аплинка, поэтому внутренний
  трафик контейнеров (docker0/br-*, veth) не затрагивается.

## Структура

```
server/
├── ansible.cfg
├── inventory.ini          # хосты и группы
├── site.yml               # точка входа, теги = команды bin/ops
├── bin/ops                # обёртка: ставит ansible, выбирает тег
├── bin/collect-secrets    # сборка ключей всех хостов в gpg-архив (без Ansible)
├── group_vars/
│   ├── all.yml            # не-секретные настройки
│   └── vault.yml.example  # образец секретов (шифровать ansible-vault)
├── host_vars/             # параметры по каждому хосту: что бэкапить, что считать нормой
└── roles/
    ├── audit/             # read-only проверки и отчёт
    ├── restic_backup/     # развёртывание бэкапа + шаблоны скриптов + verify
    ├── s3_keys/           # ротация ключей с проверкой и откатом
    ├── docker_firewall/   # правила DOCKER-USER
    └── cleanup/           # удаление легаси (opt-in)
```
